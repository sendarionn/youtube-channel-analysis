# 品質基準と評価方法

バージョン 1.1.0

## 1. データの品質基準

| 項目 | 基準 | 確認方法 |
|---|---|---|
| 網羅性 | 公開動画の取得率 95% 以上。取得できない動画（メンバー限定など）は理由を記録 | 一覧の本数と `videos/` の件数、ログ |
| 重複・欠損 | video_id の重複 0。欠損は件数と理由を記録 | `reports/<slug>/robustness.md` データ品質 |
| 出典 | raw の各スナップショットに manifest.json（出典・方法・日時） | ファイルの存在 |
| 異常値 | 登録者数の急減は異常値として除外し、件数を記録 | `channel_history.csv` の `anomaly` |
| 再現性 | 同じ raw と同じバージョンから同じ processed・表・図ができる | `ycanalysis.analyze.baseline <slug> check`、回帰テスト |

## 2. 分析の品質基準

- 主要な結論は、[metrics.md](metrics.md) の代替指標でも向きと有意性が保たれる（`analyze.robustness`）
- 手作業の分類に依存する結論は、規則ベースまたは再判定との κ ≥ 0.6 を満たす。満たさない場合は確信度を1段下げる
- 各群5本未満の比較で検定しない。小標本の群間差は「記述」と書く
- 相関から因果を書かない。交絡の候補を最低1つ挙げる
- 反例（結論に合わない動画）を最低1本、URL つきで挙げる

## 3. 仮説の評価基準（報告書7章）

各仮説について「支持・反証・代替説明・確信度・再現可能性」を書く

| 確信度 | 条件 |
|---|---|
| 高 | 2つ以上の独立した根拠（例：手作業と規則、複数の指標）で一貫し、反例が説明できる |
| 中 | 根拠は一貫するが、交絡・判定バイアス・小標本のどれかが残る |
| 低 | 根拠が1つだけ、または公開データで直接検証できない |
| 棄却 | 期待した差が複数の指標で見られない |

| 再現可能性 | 条件 |
|---|---|
| 高 | 企画・編集・運営の方法で、発信者の属性に依存しない |
| 中 | 方法は真似できるが、能力・資源（制作量・専門知識）が必要 |
| 低 | 発信者の経歴・人柄・時流に依存する |

ジャンル横断の一般化は、同じバージョンの方法で調べた比較可能な事例が3件以上そろうまで行わない

## 5. 改善サイクル

**調査 → 評価 → 問題発見 → 改善案 → 検証 → 採用・却下 → 次回調査**

1. 調査の後、`methodology/reviews/<日付>-<slug>.md` にレビューを書く（データ収集・定量・定性・結論ごとの根拠）
2. 問題ごとに改善案を作る
3. 改善案は、同じデータに旧方式と新方式を適用して比較する
   - 分類：κ、未分類率、規則と手作業での効果の一致
   - 指標：主要な結論の向き・有意性、外れ値への感度
   - 収集・処理：実行時間、失敗率
4. 判断
   - 採用：改善が数値で確認できた
   - 保留：効果が不明確、または検証に必要なデータがない
   - 却下：改善しない、または悪化した
   - 「新しい方法の方が高度だから」は採用理由にしない
5. 採用したら [CHANGELOG.md](CHANGELOG.md) に記録し、`METHODOLOGY_VERSION` を上げる
   - 結果が変わる変更（指標・分類・選定）はマイナー以上、結果が変わらない変更（設定化・高速化）はパッチ
6. 回帰テスト（`pytest`、`ycanalysis.analyze.baseline <slug> check`）で既存の調査が壊れていないことを確認する
   - 結果が変わる変更なら、基準値を更新する前に変化を CHANGELOG の「既存分析への影響」に書く
7. 異なるバージョンの結果をそのまま比較しない。必要なら旧データを新方式で再分析する
